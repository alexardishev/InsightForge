# CDC: эксплуатация

Как настроить базы-источники, что значат предупреждения CDC в логах сервиса и что делать в аварийных ситуациях.

## Как устроен CDC

```
Postgres-источник ──► Debezium (Kafka Connect) ──► Kafka ──► сервис ──► DWH
  слот slot_<source>     коннектор conn_<source>    топики dbserver_<source>.<schema>.<table>
  публикация pub_<source>                            ошибки, которые нельзя исправить повтором: <topic>.dlq
```

- `<source>` — имя источника из `oltp_connections[].name`.
- Сервис коммитит позицию в Kafka только после записи события в DWH. Если сервис остановлен, события ждут в Kafka (см. «Отставание»).
- **Слот репликации** — закладка в Postgres «Debezium прочитал до этой позиции». Пока закладка не сдвинется, Postgres не удаляет журнал (WAL) после неё. WAL один на весь сервер Postgres: слот держит записи **всех** баз сервера, а не только своей.

## Настройка Postgres-источника

| Настройка | Зачем |
|---|---|
| `wal_level = logical` | Без неё Debezium не работает. |
| `max_replication_slots`, `max_wal_senders` | Не меньше числа источников на сервере плюс уже используемые слоты. |
| `max_slot_wal_keep_size` (Postgres 13+) | **Жёсткий лимит WAL, который может удерживать слот.** Без лимита остановленный Debezium копит WAL, пока не заполнит диск, и Postgres останавливается. С лимитом при превышении Postgres помечает слот потерянным (`lost`) и продолжает работать; CDC по источнику придётся восстановить (см. ниже). Значение подбирается под свободное место на томе с WAL. Настройка действует на **все** слоты кластера, включая слоты физических реплик, поэтому её нужно согласовать с DBA. |

Также:
- **Держите DWH и системную БД сервиса на отдельном сервере.** Если они на одном сервере с источником, их запись (особенно ETL) растит общий WAL, а слот «тихого» источника его держит.
- **Пользователь Debezium** (`connection_string_kafka`) — с правом `REPLICATION`. Если задана `heartbeat_table`, ему нужно ещё право создавать таблицы в её схеме.

## Heartbeat

- Всем коннекторам выставляется `heartbeat.interval.ms = 10 s`: Debezium регулярно подтверждает позицию слота.
- Этого мало, если база-источник «тихая» (изменений почти нет), а другие базы сервера пишут много. Debezium не получает событий из своей базы, подтверждать ему нечего, и слот стоит. Для такого источника задайте таблицу heartbeat:
  ```yaml
  oltp_connections:
    - name: quiet_db
      connection_string: ...
      connection_string_kafka: ...
      heartbeat_table: public.insightforge_heartbeat
  ```
  При старте сервис создаёт таблицу (`id integer PRIMARY KEY, ts timestamptz`) под пользователем из `connection_string_kafka`. Debezium раз в 10 с перезаписывает в ней одну строку, это изменение двигает слот. Если создать таблицу не удалось, в логе будет «Не удалось создать heartbeat-таблицу», а коннектор зарегистрируется без неё.
- Понять, что heartbeat-таблица нужна, можно по наблюдателю: слот активен, но удерживаемый WAL растёт.

## Наблюдатель за слотами (`wal_watch`)

```yaml
wal_watch:
    interval: 1m            # как часто проверять
    retained_warn_mb: 5120  # порог предупреждения об удерживаемом WAL
    # disabled: true        # выключить наблюдатель
```

Раз в `interval` сервис смотрит `pg_replication_slots` на серверах источников. Слоты сервис **не удаляет**.

| Сообщение в логе | Что значит | Что делать |
|---|---|---|
| `Слоты репликации` (INFO) | Сводка: сколько слотов, максимум удерживаемого WAL. | — |
| `Слот репликации источника не найден` | Коннектор не создан или слот удалён. | Проверить коннектор: `GET <connect>/connectors/conn_<source>/status` и логи Connect. |
| `Слот репликации неактивен` | Debezium не читает слот, WAL копится. | Поднять Kafka Connect / коннектор. |
| `Слот репликации держит много WAL` | Удерживается больше `retained_warn_mb`. | Если слот неактивен — как выше. Если активен — источник «тихий»: задать `heartbeat_table`. |
| `Слот репликации вот-вот будет потерян` (ERROR) | WAL слота превысил `max_slot_wal_keep_size`. | Срочно восстановить чтение (Connect). Иначе слот станет `lost`. |
| `Слот репликации потерян` (ERROR) | CDC по источнику остановлен. | «Восстановление после потери слота». |
| `Слот репликации не относится к источникам из конфига` | Слот удалённого источника или другого экземпляра сервиса. | Если источник действительно удалён — «Удаление источника». |
| `У Postgres не задан max_slot_wal_keep_size` | Нет защиты от заполнения диска. | Задать лимит вместе с DBA. |

## Отставание и срок хранения в Kafka

- `kafka.debezium_topic_retention` (по умолчанию в конфигах 336h = 14 дней) — сколько Kafka хранит события. Если сервис отстанет больше, Kafka удалит события непрочитанными и в DWH они не попадут.
- Раз в 30 с в логе сводка `Отставание CDC`: непрочитанные сообщения и возраст последнего полученного события. Если партиция отстаёт дольше половины срока хранения, будет предупреждение `Отставание CDC приближается к сроку хранения топика` — до потери ещё есть время, нужно восстановить обработку.
- Если срок хранения всё же превышен, изменения за этот период потеряны: перезапустите ETL затронутых вьюх.
- `kafka.dlq_retention` (720h) — срок хранения `<topic>.dlq`. В DLQ попадают события, которые нельзя обработать повтором (битый JSON, удалённая вьюха). В заголовках сообщения — исходные топик, партиция, offset и текст ошибки.

## Восстановление после потери слота

У коннекторов `snapshot.mode = never`: после потери слота Debezium сам ничего не перечитает. Изменения за время, пока слот был потерян, придётся загрузить заново через ETL.

1. Удалить коннектор:
   ```bash
   curl -X DELETE http://<connect>:8083/connectors/conn_<source>
   ```
2. Удалить потерянный слот в базе-источнике (публикацию `pub_<source>` можно оставить):
   ```sql
   SELECT pg_drop_replication_slot('slot_<source>');
   ```
3. Перезапустить сервис: он зарегистрирует коннектор, а Debezium создаст новый слот и начнёт читать с текущей позиции.
4. Перезапустить ETL всех вьюх, в которых есть таблицы этого источника.

## Удаление источника (брошенный слот)

Пока в сервисе нет команды удаления источника — вручную:

1. Убрать источник из `oltp_connections` и перезапустить сервис.
2. Удалить коннектор:
   ```bash
   curl -X DELETE http://<connect>:8083/connectors/conn_<source>
   ```
3. Убедиться, что слот неактивен и **не используется другим экземпляром сервиса** (имена слотов общие для всего кластера Postgres):
   ```sql
   SELECT slot_name, active FROM pg_replication_slots WHERE slot_name = 'slot_<source>';
   ```
4. Удалить слот и публикацию:
   ```sql
   SELECT pg_drop_replication_slot('slot_<source>');
   DROP PUBLICATION IF EXISTS pub_<source>;
   ```

## Безопасность

REST API Kafka Connect (`8083`) отдаёт конфиги коннекторов вместе с паролями к базам-источникам. Не публикуйте этот порт наружу: доступ к нему нужен только сервису.
